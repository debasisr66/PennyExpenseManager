Chapter one A small promise with clear boundaries

The first decision was to keep the product modest. Penny was not designed as a bank, a social network or an accounting system. It had one job: let a person add an expense, understand the month, and feel in control. That boundary made the interface easier to learn and easier to trust.

The product choice: build the ordinary path first. Date, amount, category and description came before automation. The monthly total, budget warning and category chart made the result visible immediately.

Chapter two Making the app feel like daily life

Once the basic flow worked, the app gained the details that make a personal tool feel natural: searchable tags such as #groceries, the way a payment was made, INR as the default currency, and a visible What’s New area. Import and export were included so the user always has a way to take their information with them.

Progressive enhancement

Typing remains the reliable starting point. Voice is helpful when it works, never required.

Human in the loop

A voice-created draft is reviewed before it changes an expense. Penny does not save an unheard or misunderstood amount.

Portable by default

Explainable feedback

Search, voice and budget messages say what happened and what the person can do next.

The voice glitch that changed the design

Voice looked like one feature. Real mobile testing showed it was a chain of different experiences.

What we saw

A transcript could end early, a later attempt could fail, and language conversion could report that it was offline.

What we learned

Voice capture is separate from understanding the expense. A clever guess is worse than a visible question in a money app.

What Penny does now

Keep useful partial words, restart cleanly, read common expense facts on the device, and require review before saving.

The turning point: Penny stopped treating voice as a promise of perfect translation. It treats voice as one way to capture text, then reads the useful facts in an expense - amount, date, category and payment method - and shows a plain English draft. The person checks it before saving.

The architecture in plain language

Penny screen

Where a person records, searches and reviews spending.

Browser storage

Where expenses and budgets stay on the person’s device.

Optional helpers

Voice capture and requested currency rates support the main experience.

GitHub and Docker

Where the published app, evidence and portable local run path live.

The important architectural choice is that personal expense data remains with the browser. Penny can be published through GitHub Pages or served locally through Docker without becoming a server-side data system.

Quality habits that became part of the product

Security

Validate inputs, protect imports, avoid unsafe content, and review common web risks before release.

Privacy

Keep expense data in the browser, start voice only when requested, and make exports a user choice.

Reliability

Offer keyboard entry and clear recovery messages when voice or a network helper is unavailable.

Mobile use

Test the real small-screen journey, not only a desktop browser made narrow.

GitHub discipline

Keep the code, release notes, tests and results together so a change can be understood later.

Release evidence

Publish test cases and results as documents, rather than placing test controls in the app itself.

The Docker chapter

Docker did not change what Penny is. It made the same tested app easier to run from a machine. The container is deliberately small: it serves the Penny files, checks its own health, and does not hold anyone’s spending data. A simple Penny command starts and stops it locally when Docker Desktop is available.

The principle: make the path to run the app as understandable as the path to use it. A local command should feel like a product action, not an engineering project.
